Survey (Phase 1)
  uname at start of task: 7.2.9-t9
  Baseline tree: /home/kernelmaster/kernel-build/linux-7.2.9-baseline (not modified).
  In-tree ZC recv paths already present and ENABLED in .config:
    CONFIG_IO_URING_ZCRX=y
    CONFIG_NET_DEVMEM=y
    CONFIG_PAGE_POOL=y
  Source present: io_uring/zcrx.c, net/core/devmem.c, tcp_recvmsg_dmabuf(),
  Documentation/networking/{iou-zcrx,devmem}.rst.

  Both ZC paths require NIC hardware features the docs call out:
    - Header/data split (ethtool tcp-data-split)
    - Flow steering + RSS carve-out for ZC queues
    - Driver memory-provider / queue_mgmt support so payloads land in
      registered userspace/dmabuf memory (headers still go to kernel)

  Evidence this host cannot use either path:
    1. ethtool -g enp3s0f0: "TCP data split: n/a", "HDS thresh: n/a"
    2. sudo ethtool -G enp3s0f0 tcp-data-split on ->
         "setting TCP data split is not supported" / EOPNOTSUPP
    3. Driver is ixgbe for Intel X550 — no tcp-data-split / memory-provider
       path usable on this NIC (ZC selftests target mlx5/bnxt/ice-class HW).
    4. Loopback has no HW RX queue memory provider.
    5. IORING_REGISTER_ZCRX_IFQ as root on enp3s0f0 and lo:
         errno=95 (EOPNOTSUPP). Without CAP_NET_ADMIN: errno=1 (EPERM).
    6. MSG_SOCK_DEVMEM recvmsg on localhost TCP: receives bytes but no
       SCM_DEVMEM_* cmsg (errno recorded as ENODATA / 61 in probe).
    7. ZCRX_REG_NODEV exists but docs say "All data will be copied" —
       that is a copy fallback, not a zero-copy win, so it was not used
       as a pass path.

  A minimal "unlock socket during skb_copy_datagram_msg" kernel change was
  considered and rejected: not clearly safe (concurrent writers / TOCTOU
  under sk_lock), and would not be an enablement of the in-tree ZC path the
  roadmap points at. No fake kernel win.
