Roadmap ask
  "Use the fast util estimate for placement; do not rip out PELT."
  UTIL_EST already on. Fixed-window (Android WALT) is the published alternative
  for the ramp. Do not remove PELT — schedutil depends on it.
  Workload: General purpose. Impact: Medium.

Survey — what already existed (full notes: reports/task11-survey.txt)
  - SCHED_FEAT(UTIL_EST, true); live debugfs shows UTIL_EST (toggleable via
    echo NO_UTIL_EST|UTIL_EST > /sys/kernel/debug/sched/features).
  - util_est_update() on dequeue: snap-up on util increases; EWMA w=1/4 on
    decreases; margin / runnable guards.
  - task_util_est(p) = max(PELT util_avg, util_est).
  - Placement already reads util_est: task_fits_cpu, EAS/asym fits,
    cpu_util() max(util_avg, util_est), energy busy_time, several LB sites.
  - Holdouts using bare task_util(): cache-aware LLC helpers — N/A on 1 LLC.
  - No Energy Model on this box → EAS idle. Homogeneous cpu_capacity=1024 →
    asym capacity fitting is a no-op.
  - WALT / fixed-window would be a major redesign parallel to PELT; out of
    scope for a gated Task 11 patch (and roadmap forbids ripping out PELT).

Decision (Approach A)
  Stock util_est is already wired into placement. Prefer measuring existing
  behavior + the safe debugfs knob over inventing a patch. No 7.2.9-t11,
  no 0011-*.patch, baseline tree untouched.

Harness (Task 11)
  1. New workload util_est_burst (C): 12 burst workers (5 ms ON / 80 ms OFF)
     + 4 always-on hogs. OFF ≈ 2.5× PELT half-life so util_avg decays while
     util_est EWMA can still hold. Reports wl_bursts_per_sec, wl_wake_lat_*,
     wl_burst_migrate_frac, wl_sched_feat_util_est.
  2. tasks.conf Task 11 → util_est_burst wake_llc general; primary metrics
     expanded with burst wl_* + ttwu_remote_delta.
  3. workloads.conf / lib/common.sh / compare.sh labels wired.
  4. A/B on same baseline kernel: UTIL_EST=ON (stock) vs NO_UTIL_EST.

What was NOT done (and why)
  - No kernel patch: placement already uses task_util_est / cpu_util util_est.
  - No WALT: not a gated one-feature change; would fight "do not rip out PELT."
  - No fake placement wins on 1 LLC / no EM / homogeneous CPUs.

How to read (util_est_burst)
  Throughput is bit-identical work: 2124 bursts every run, bursts/sec within
  ±0.03 (~0.02% relative) across ON and OFF. wake_lat_p50 stuck at 48 us
  (timer/nanosleep granularity), not a placement signal.
  migrate_frac / cpu_migrations / ttwu_remote / wake_lat_p99 flip sign across
  pairs and the within-arm range already covers the between-arm gap — no
  same-sign 3-pair win for UTIL_EST ON vs OFF.
  Interpretation: on this homogeneous single-LLC box without an Energy Model,
  turning util_est off does not move burst placement throughput. That does
  NOT mean util_est is unused in the source — it means the knob cannot be
  excited into a measurable win here. Stock default ON remains correct.

Secondary — wake_llc / general (regression context only)
  wake_llc cpu_migrations are highly noisy on both arms (ON: 8k–25k;
  OFF: 11k–50k). general cycles ≈ 149.2–149.9e9 both arms. No same-sign
  util_est-attributable delta. Not used as the Task 11 pass gate.

Verdict: PASS (policy / in-tree)
  - UTIL_EST is already ON and placement already uses task_util_est /
    cpu_util util_est path in 7.2.9 CFS.
  - Debugfs A/B (ON vs NO_UTIL_EST) on bursty load shows no measurable
    placement benefit on this hardware (noise-bound).
  - No gated kernel change is justified; WALT is out of scope.
  - Harness now has a dedicated util_est_burst workload for future boxes
    (asym capacity / EAS / multi-LLC) where the knob could matter.
