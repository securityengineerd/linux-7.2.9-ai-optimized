Survey (Phase 1)
  Roadmap: "Take direct reclaim and direct compaction off the allocating task."
  Keep the direct path available; stop using it on latency-sensitive faults.
  Prefer fail-fast to order-0; let kswapd/kcompactd keep higher orders warm.

  __alloc_pages_slowpath() (mm/page_alloc.c):
    can_direct_reclaim = gfp & __GFP_DIRECT_RECLAIM;
    can_compact = can_direct_reclaim && gfp_compaction_allowed();
    wake_all_kswapds → direct reclaim → direct compact → may_oom.
    __GFP_NORETRY limits retry; costly orders skip retry without RETRY_MAYFAIL.

  THP fault GFP is already policy-gated by vma_thp_gfp_mask()
  (/sys/kernel/mm/transparent_hugepage/defrag):
    always        → GFP_TRANSHUGE (±__GFP_NORETRY) = sync compact/reclaim on fault
    defer         → GFP_TRANSHUGE_LIGHT|__GFP_KSWAPD_RECLAIM = wake background, no direct
    defer+madvise → LIGHT; direct only if VM_HUGEPAGE
    madvise (stock)→ LIGHT; direct if VM_HUGEPAGE (MADV_HUGEPAGE)
    never         → GFP_TRANSHUGE_LIGHT only

  Stock THP enabled=[madvise], defrag=[madvise]. So madvised THP faults STILL
  take __GFP_DIRECT_RECLAIM today — Task 7's intent for THP is expressed by
  switching defrag to defer/never, not by a new sysctl.

  Order-0 / GFP_USER paths still require direct reclaim under watermark
  pressure; skipping that ungated is an OOM footgun. Existing knobs
  (swappiness, watermark_scale_factor, compaction_proactiveness) tune
  background behavior without removing the direct path.

  Full prep: reports/task7-survey-prep.txt.

Policy under test (already in-tree)
  A = transparent_hugepage/defrag=always  (max sync compact on THP fault)
  B = transparent_hugepage/defrag=defer   (wake kswapd/kcompactd; no direct)
  Same mem_pressure fragment recipe; free variable = defrag policy only.
  Stock madvise+ MADV_HUGEPAGE is closer to always for this workload
  (also sets __GFP_DIRECT_RECLAIM); always is the clearer "direct on" pole.

How to read
  Pass gate: lower allocating-task stall under proven pressure, no OOM.
  compact_stall_delta: always ∈ [965,1190] on all 3 runs; defer = 0 on all 3.
  Same sign, far past run-to-run noise → direct compaction is OFF the fault
  path under defer. That is the Task 7 mechanism for THP.
  wl_alloc_fault_ns: defer lower on all 3 pairs (ratios 0.20–0.88). Pair 3
  is helped by a warm buddy after prior runs (defer got full 1536 THP with
  0 fallback); pairs 1–2 show the expected tradeoff — fewer THP wins
  (677/716 vs 1536) and more thp_fault_fallback (859/820) when compact is
  not allowed to stall the fault. Latency still improves because fallback
  to order-0 avoids sync compact.
  OOM: zero across the board — risk gate held for this policy.

Whole-run perf (wraps fill+punch+alloc; not the free variable)
  always wall ~9.4–9.6s; defer wall ~9.3–9.4s. cycles similar — dominated
  by the shared fill/punch setup, not the THP alloc phase.

Reclaim-mode smoke (not the formal A/B)
  mem_pressure -m reclaim on t9 earlier: pgscan_direct_delta=+449,
  pgscan_kswapd_delta=+111261, oom=0. Proves direct reclaim is reachable
  on this box. Intentionally NOT skipped by any patch.

Verdict
  PASS (policy / existing sysfs) — use transparent_hugepage/defrag=defer
  (or never) to take direct compaction/reclaim off THP page faults; keep
  stock madvise if THP success rate under fragmentation matters more than
  fault latency. Do NOT ship an ungated order-0 reclaim skip.
  No 7.2.9-t7 / 0007-*.patch.

Recommendation
  - Latency-sensitive hosts that MADV_HUGEPAGE heavily: set
      echo defer > /sys/kernel/mm/transparent_hugepage/defrag
    (or defer+madvise if only some VMAs should stall). Persist via udev/sysctl
    drop-in / boot script; stock default remains madvise.
  - Keep vm.compaction_proactiveness > 0 so kcompactd can warm high orders
    in the background (stock 20 is fine).
  - Leave direct reclaim on for GFP_KERNEL / order-0; tune watermarks /
    swappiness instead of removing the path.
  - Task 8 (stop reclaim from splitting large anon folios) also carries an
    MM risk note — survey-only until a pressure harness for folio-split is
    ready; do not start a patch without the same OOM gate.
