Roadmap ask
  "Move softirq and RCU callback storms out of irq-exit where tail latency
   matters." Impact: Medium for tail latency; Low if nocb and RT already on.
  Better mechanism: already config, not new code —
     CONFIG_PREEMPT_RT threads softirq;
     CONFIG_RCU_NOCB_CPU moves callbacks to kthreads.
  "Always deferring costs throughput, so this is a workload choice."
  Workload: Networking, storage.

Survey — what already existed (full notes: reports/task12-survey.txt)
  - irq_exit_rcu → __irq_exit_rcu → invoke_softirq(): on non-RT stock,
    softirq runs INLINE (__do_softirq / own stack) unless force_irqthreads().
  - handle_softirqs budget: MAX_SOFTIRQ_TIME=2 ms, MAX_SOFTIRQ_RESTART=10;
    overflow wakes ksoftirqd.
  - CONFIG_PREEMPT_RT is NOT set; CONFIG_IRQ_FORCED_THREADING=y;
    threadirqs early_param enables force_irqthreads_key.
  - CONFIG_RCU_NOCB_CPU=y but DEFAULT_ALL not set; stock cmdline has no
    rcu_nocbs → no rcuo* offload.
  - rcutree.use_softirq=Y (boot-only 0444): RCU core via RCU_SOFTIRQ on
    the softirq/irq-exit budget; =0 uses rcuc kthreads instead.
  - ksoftirqd/N already exist for overflow; they do not move the common
    case off irq-exit by themselves.
  - net.core.netdev_budget=300 / usecs=2000 are NAPI spend caps, not offload.

Decision (Approach A — existing knobs)
  Prefer measuring stock irq-exit softirq + documenting/A-B'ing boot knobs
  over inventing a gated irq_exit rewrite. No 7.2.9-t12, no 0012-*.patch,
  baseline tree untouched.

  - No always-on default for deferral: measurements show cost, not a free win.

How to read (softirq_storm)
  Softirq ON irq path (STOCK) is proven: ~20.3M softirqs / 15 s with
  ksoftirqd_ms_delta=0 on all three STOCK runs — handlers ran inline on
  irq-exit, not in ksoftirqd.
  DEFER knobs do what the roadmap describes:
    - RCU softirq delta → 0; 15 rcuo* kthreads appear (nocb offload).
    - ksoftirqd_ms_delta → 80–130 ms (threadirqs moves softirq off inline).
  Wake-lat p50/p99 stuck at the 1 ms nanosleep / log2 bucket — not a useful
  placement/tail signal here. max/avg are noise-bound across arms.
  Same-sign DEFER regressions across all 3 pairs:
    - wall_time_sec higher (~+7–9%)
    - ipc lower (~1.49–1.53 vs ~1.61–1.64)
    - rq_latency_ns much higher (~1.3–1.5 us vs ~90–100 ns)
  Softirq total count is slightly lower under DEFER (~−5 to −10%) — deferred
  path does less inline work / different batching, not a latency win.
  No RCU stall warnings on either arm.

Secondary — networking / storage (regression context)
  iperf3 loopback (8 s), 0 sender retransmits both arms:

    DEFER: 77.6 / 78.6 / 76.2 Gbits/sec

  networking throughput under this load.

Verdict: PASS (policy / in-tree)
  - Softirq (incl. RCU_SOFTIRQ) still runs on the irq-exit path on stock
    7.2.9-baseline; ksoftirqd is overflow-only until threadirqs.
  - Existing boot knobs (threadirqs, rcu_nocbs=, rcutree.use_softirq=0)
    successfully move softirq/RCU off that path — matching the roadmap's
    "already config, not new code" guidance.
  - On this box under softirq_storm, DEFER does not improve wake/tail latency
    and same-sign worsens wall time, IPC, and rq_latency. Always-on deferral
    would be the wrong default (roadmap already warns about throughput cost).
  - No gated kernel change is justified. Treat deferral as a workload /
    deployment choice (RT / nocb / threadirqs), not a new default.
  - Harness now has softirq_storm for future boxes/loads where irq-tail
    latency might show a real win.
