What the patch does
  - get_pref_llc: comment only (logic unchanged in this tree).
  - can_migrate_llc_task: ignore preferred LLC when it is off numa_preferred_nid.
  - migrate_degrades_llc: refuse migrate_load pulls off preferred LLC until
    nr_balance_failed past cache_nice_tries.

Hardware caveat (critical)
  Workload reports wl_numa_nodes=1 and wl_llc_domains=1 on every run. With a
  single LLC, llc_id(src)==llc_id(dst) for every on-box migrate, so the new
  migrate_load / preferred-LLC guard almost never fires. The NUMA half also
  cannot be proven on one socket. This run is a regression screen, not a proof
  of the Task 2 design.

Verdict: INCONCLUSIVE on this box — not a claimed win, not a clear fail.
  - Throughput and settle-migration metrics sit inside stock run-to-run noise.
  - cpu_migrations tick up a little on all three pairs; absolute change is tiny.
  - cache_misses look better on every pair and sit under stock's best run, but
    stock alone swings 1.4M-3.3M (~85% noise), and with one LLC the patch's
    intended guards largely cannot act. Treat the miss drop as interesting but
    unproven (possible boot/session effect).
  - NUMA half of Task 2 was never testable here.

Recommendation
  1. Keep the Task 2 patch in the tree as the candidate for multi-LLC / multi-
     NUMA hardware; do not treat this host as proof.
  2. On this box, either park Task 2 as "no decision" and move to the next
     task that this hardware can stress (e.g. Task 9 lockless io_uring, Task 4
     TCP, Task 5 buffered-read), or add a synthetic multi-LLC-ish affinity
     storm that still only proves migration count behavior, not cache wins.
  3. Leave GRUB on 7.2.9-baseline (current boot) until the next task build;
     7.2.9-ai-opt stays installed for re-entry.

Caveats
  - Patched and stock were collected about two hours apart on different boots.
  - 3 runs per side. migrate_storm reports 1 LLC domain / 1 NUMA node always.
